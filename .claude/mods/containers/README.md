# containers

csb サンドボックス（`csb`、`.claude/hooks/claude_sandbox.py`）と、ローカルの Docker コンテナ・Compose プロジェクトの状態を、
ペインに一覧する Claude Code の mod です。この mod 自身は、コンテナにも csb の状態にも変更を加える操作をしません（走らせるのは、下の 3 つの固定のコマンドだけです）。
ただし「読み取り専用」ではありません。`csb status` は、呼ばれるたびに、期限の切れた `csb net on` の窓を切断します（csb がどのサブコマンドでも最初に行う処理です）。
`/containers` を実行するたびと、ペインを開いている間は 10 秒ごとに `csb status` を呼ぶので、そのたびに、期限切れの窓を切断する主体がこの mod になります。
接続を切る向きの（安全側の）動きで、接続を増やすことはありません。

## 読み込み

`.claude/settings.json` の `env.CLAUDE_CODE_PLUGIN_DIRS` に `~/.claude/mods/containers` が入っていれば、
セッション開始時に読み込まれます。設定を変えたときは Claude Code を再起動してください。

## 使い方

```text
/containers      ペインを開いて、サンドボックス・コンテナ・Compose の状態を表示
```

引数は取りません（付けると使い方を返すだけで、何も実行しません）。ペインを開いている間は 10 秒ごとに読み直します（そのたびに `csb status` を呼びます。上のとおり、期限切れの `net on` の窓の切断が起こりえます）。

### ペインの操作

| キー   | 動作                                     |
| ------ | ---------------------------------------- |
| `r`    | すぐに読み直す                           |
| 閉じる | ペインを閉じる。閉じると読み直しも止まる |

### 表示について

ペインは 3 つの区分に分かれ、区分ごとに独立して取得します。ある区分が取れなくても、ほかの区分は表示します。
取れなかった区分は、タイトルに「取得できず」と出て、理由を 1 行で示します（stderr の中身は出しません）。

| 区分                 | 内容                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------ |
| サンドボックス       | ID・状態・役割・ネットワーク・リポジトリ（`~` 相対）・パッチごとの verify とレビューの状態 |
| その他のコンテナ     | 名前・イメージ・状態。bind mount があれば `[bind mount あり]` の印                         |
| Compose プロジェクト | 名前・状態・設定ファイル（`~` 相対。2 つ目以降は `(+N)`）                                  |

- **サンドボックス**
  - 状態は csb が返す `container`（`running` / `exited` など）です。docker に届かなければ `?` になります。
  - 役割（`work` / `setup` / `verify`）は、コンテナのラベル `dev.claude.sandbox.role` から引きます。
    - `docker ps` を最後まで読めて、そのサンドボックスのコンテナが無ければ `-` です。
    - `docker ps` を読めない・出力が途中で切れたときは `不明` です（「無し」には見せません）。
  - ネットワークは、csb の `net_connected`（実際の接続）と `net_expired`（期限が過ぎた記録）から、5 つの状態を出します。

    | 状態       | 条件                                                | 表示                                           |
    | ---------- | --------------------------------------------------- | ---------------------------------------------- |
    | `on`       | 接続中で、`csb net on` の期限内                     | `接続中 (HH:MM まで)`                          |
    | `expired`  | 接続中だが、期限を過ぎている                        | `接続中 (期限切れ。次の csb の呼び出しで切断)` |
    | `nowindow` | 接続中だが、期限の記録が無い                        | `接続中 (期限の記録なし)`                      |
    | `off`      | 切断                                                | `切断`                                         |
    | `unknown`  | 確かめられない（docker に届かない・照合に通らない） | `不明`                                         |

    `net_connected` を持たない古い csb の出力では、`net_on_until` が期限内なら `on`、そうでなければ `off` です。
    csb は、`csb status` の呼び出しの先頭（行を読む前）に、期限切れの窓を切断します。そのため `expired` が見えるのは、切断できなかったとき（そのサンドボックスの lock が取れない・切断に失敗した）だけで、次の読み直し（ペインを開いている間は 10 秒ごと）でもう一度切断を試みます。

  - パッチは `patch <sha 先頭 7 桁>  verify <PASS/FAIL/MISSING/STALE>  <レビュー>=<pass/fail/unresolved/stale/missing> ...` の 1 行です。
    csb の出力には「最新のエクスポート」を決める材料（時刻）が無いため、「最新の 1 件」ではなく **全パッチを csb の並び（sha 順）で** 出します。
  - サンドボックスのコンテナに bind mount があると `[bind mount あり]` が赤で出ます。csb のサンドボックスにはあってはならないものです。
    取れていないとき（`docker ps` を読めない・出力が途中で切れて、見えた分には無かった）は `[bind mount 不明]` を黄色で出し、無いことの確認とは見せません。
  - csb の状態があるサンドボックスのコンテナは、この区分に畳み、「その他のコンテナ」には出しません。
    畳むのは、ラベルの ID と、csb が付けるコンテナ名（`csb-<ID>` / `csb-<ID>-setup` / `csb-<ID>-verify`）の ID が合うものだけです。
    ラベルは誰でも付けられる（別のラベルの値にカンマで埋め込むこともできる）ので、ラベルだけ似せたコンテナは畳まず、「その他のコンテナ」に `[csb ラベル]` 付きで残します。

- **その他のコンテナ**
  - `docker ps -a` の全件が対象です。csb のラベルを持つが csb の状態と結びつかないコンテナ（csb が無い・状態を消した後の残りなど）は `[csb ラベル]` の印を付けて残します。
  - bind mount は `docker ps` の `Mounts`（ボリューム名とホストのパスを並べたもの）に、絶対パスがあるかで判定します。パスそのものは表示しません。
  - 各区分に出す行は 40 件までで、超えた分は `他 N 件` と件数だけ出します。
- **Compose プロジェクト**
  - `docker compose ls`（既定では実行中のプロジェクトだけ）の結果です。

環境変数・コンテナの Command・ラベルの中身・マウントのパスは取得も表示もしません。
docker や csb の出力に混じる端末制御文字・表示を偽る文字（bidi の書き換えなど）は、描く前に `U+FFFD` に置き換えます。
ホームディレクトリ配下のパスは `~` に置き換えて表示します。

取れなかったときの知らせ（区分ごとに 1 行）:

| 状況                                                             | 知らせ                                                                                  |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `docker` が無い・5 秒以内に終わらない                            | `docker ps を実行できませんでした (未導入か、5 秒以内に…)`                              |
| Docker デーモンに繋がらない                                      | `Docker デーモンに接続できません (Docker が起動していますか)`                           |
| Docker のソケットに権限が無い                                    | `Docker のソケットを使う権限がありません (実行ユーザーの権限を…)`                       |
| `docker compose` プラグインが無い                                | `docker compose が使えません (プラグインが入っていません)`                              |
| csb のラッパー（`~/.local/bin/csb`）が無い・通常のファイルでない | `csb が使えません (~/.local/bin/csb が無いか、通常のファイルでない。install.sh を実行)` |
| `HOME` が取れない・絶対パスのディレクトリでない                  | `csb が使えません (HOME が絶対パスのディレクトリでない)`                                |
| ほかの失敗・出力を読めない                                       | `<コマンド> が失敗しました (exit N)` / `…の出力を読めませんでした`                      |

### ペインを描けない環境

ペインを置けない環境では、コマンドの返り値に件数と、区分ごとの先頭 20 行を返します（超えた分は `他 N 件`）。
この一覧はモデルも読むので、パッチの行や絶対パスは載せません。

## 起動するプロセス

この mod が起動するプロセスは、次の 3 つの固定の argv だけです。どれも `$.process.run` で、シェルを通さず、5 秒の timeout を付けて、並べて走らせます。
`csb` は、`install.sh` が書く固定のラッパー `<HOME>/.local/bin/csb` を、絶対パスで呼びます（存在を確かめてから呼びます）。
このラッパーは、信頼できる（root 所有の）`python3` を `-I -S` で起動する数行のシェルスクリプトです。
そのため、この mod は `python3` を自分では起動しません。PATH の `python3`（pyenv の shim など）を通すと、セッションの cwd にある `.python-version` などで、別のインタプリタに差し替えられるためです。
ラッパーが無い・通常のファイルでないとき（symlink も該当します。古い install が `claude_sandbox.py` への symlink を残していると、その shebang 経由で PATH の `python3` が動くためです）、`HOME` が絶対パスのディレクトリでない（取れない・相対パス・実在しない）ときは、走らせずに「csb が使えません」の知らせを出します（原因が `HOME` のときは、ラッパーのせいにせず `install.sh` も勧めない別の文面です。上の表のとおり）。`CLAUDE_CONFIG_DIR` は見ません。
symlink かどうかを見るのは最後の要素（`csb` そのもの）だけです。`~/.local` や `~/.local/bin` を、エージェントが書ける場所（リポジトリなど）への symlink にしている構成では、指す先のパスへの Edit が `~/.local/bin/csb` の保護に当たらず、この mod は差し替えられたラッパーをそのまま起動します。この mod はラッパーの中身を照合しないためです。Bash のフックの `csb_is_ours` は、この構成を受け付けません。`~/.local` と `~/.local/bin` が symlink でない本物のディレクトリであることを lstat で確かめ、ラッパーの中身もテンプレート（`_sandbox_gate.csb_wrapper_text`）と完全一致で照合します。どちらかに当たらなければ静的な allow を出しません。そのとき、境界の操作（`create` / `net on` / `apply` / `image build`）は拒否され、ほかの正規形は確認に回ります。そうした構成にはしないでください。
`HOME` が絶対パスで、ディレクトリとして実在する（`$.fs.stat` の kind が `dir`）ときだけ、3 つとも cwd を `HOME` にして走らせます（セッションの cwd は信頼できないリポジトリのことがあり、その `.python-version` や `.env` に左右されないためです）。それ以外のときは、cwd を指定しません（セッションの cwd のままです。実在しない `HOME` を cwd にすると起動に失敗し、docker まで取れなくなるためです）。このとき csb は、ラッパーが `HOME` の下にあるので走らせず、上の表の `HOME` の知らせを出します。

```text
<HOME>/.local/bin/csb status --json
docker ps -a --no-trunc --format {{json .}}
docker compose ls --format json
```

- `docker inspect` は呼びません。変更するコマンド（`rm` / `stop` / `prune` / `csb net on` など）は一切呼びません。
- `csb status --json` は、サンドボックスごとに `docker inspect`（読み取り）をして状態を照合します。csb 自身が行うもので、この mod は結果の JSON だけを読みます。
- ただし csb は、どのサブコマンドでも最初に、期限の切れた `net on` の窓を切断します（`expire_windows`）。この mod が起動するのは `status --json` だけですが、その呼び出しにも付いてくる処理なので、`/containers` を実行するたびと、ペインを開いている間は 10 秒ごとに走ります。
- `--no-trunc` を付けるのは、`Mounts` が既定では 15 文字ほどで切れ、2 つ目以降の bind mount を見落とすためです。
- 残る穴: `docker` は PATH から選ばれ、`docker compose` は `~/.docker/cli-plugins` の plugin を読みます。この 2 つはフックのレビューを通らずに、ペインを開いている間は自動で走ります。一方で、Bash から `~/.docker/cli-plugins` への書き込みは、レビューのモデルには回りますが、人への確認（ask）には回りません。そのため、そこに置かれた plugin は人の確認なしに実行されえます。直し方（保護の対象に入れる、または compose の取得をやめる）は後続の作業として残しています。

## 開発

```bash
claude plugin test .claude/mods/containers       # テスト（hooks/catalog.ts の純粋ロジックとコマンド・ペイン）
claude plugin validate .claude/mods/containers   # マニフェストとフックの検査
```

この mod はツールの実行可否には関与せず、それに関わるイベント（`tool.*` など）にはフックしません。
フックすると、bash-review や git-push-review を素通りさせる余地が生まれるためです。
一方で、上の 3 つのプロセスは Bash ツールを通さず、決まった引数でシェルを使わずに直接起動します。そのため、bash-review の審査の対象外です。
設計と安全上の前提は [docs/claude-architecture.md の「mod (関数フック)」](../../../docs/claude-architecture.md#mod-関数フック) にあります。
